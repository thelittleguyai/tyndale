Section 01 · The principle

Subset, not a separate product

The risk with a "lite version" is that you build something you later throw away. V1-Lite avoids that by obeying one rule: it shares full Tyndale's contracts from day one.

A contract is any interface or data shape that two parts of the system agree on. If V1-Lite and full Tyndale agree on the same contracts, then upgrading means adding components that speak the same language — not replacing components that spoke a different one.

The five contracts that V1-Lite must share with full Tyndale, exactly:

  • Case file schema. The Postgres record that holds a user's matter — findings, deadlines, coverage data, documents. V1-Lite writes the same fields the full version reads. When FHIR goes live later, it populates the same coverage fields that manual upload populates now.
  • Citation format. The [authority §section, src_id] format from reference/citations.md. V1-Lite's Tier B legal claims cite exactly the way full Tyndale does, so the citation resolver you build now keeps working unchanged.
  • Voice tiering. The three-tier framework from reference/voice_tiering.md. V1-Lite speaks in the same confident-advocate voice with the same tier discipline. No voice migration later.
  • Skill structure. The SKILL.md + reference-files pattern. V1-Lite ships a subset of the 8 Skills, each in the full structure. Adding the deferred Skills later is just adding directories.
  • Tool signatures. The tool descriptions from tools/descriptions/. V1-Lite implements a subset of tools, but each implemented tool matches its full-version signature exactly. The FHIR tools' return shapes are matched by the upload-path tools, so subagents never know the difference.
The test for any V1-Lite decision
"Does this create throwaway work, or expandable work?"
If a simplification means rebuilding later, it's the wrong simplification. If it means adding later, it's right. Example: building a custom V1-Lite case file schema = throwaway (you'd migrate data later). Building the full case file schema but only populating some fields = expandable (you just start populating more fields). Always choose expandable.

How this stays forward-compatible

The tool descriptions in tools/descriptions/ define what fhir_get_coverage and fhir_get_eobs return. In V1-Lite you build tools that produce the same return shape from uploaded documents:

  • upload_extract_coverage returns the same shape as fhir_get_coverage — plan name, subscriber, effective dates, deductible, coinsurance, OOP max. Source is an uploaded insurance card + plan summary instead of a FHIR Coverage resource.
  • upload_extract_eob returns the same shape as fhir_get_eobs — line items, allowed amounts, member responsibility. Source is an uploaded EOB image instead of a FHIR ExplanationOfBenefit resource.
  • bill_ocr_extract is identical to full Tyndale — it was always document-based.

When 1upHealth goes live, the FHIR tools are added alongside the upload tools. The Lead Planner gains a branch: "if the user has connected insurance, pull via FHIR; otherwise, ask them to upload." The upload path never gets removed — plenty of users will prefer uploading, and some payers won't be reachable via FHIR.

The one real cost of upload-first
OCR extraction quality is your V1-Lite risk
FHIR data is clean and structured. Uploaded documents are messy — photos of crumpled bills, low-contrast EOBs, multi-page PDFs. The extraction path needs confidence scoring: when extraction confidence is low, the Lead Planner asks the user to confirm the key numbers (per principle P1 — make the ask trivial: "I read your deductible as $2,500 — is that right?"). This is also a feature: confirmed extractions become high-quality labeled training data for the feedback loop.
Section 04 · Intelligence layer

Why this is still meaningfully better than a raw LLM

Even at three agents, V1-Lite keeps the things that make Tyndale trustworthy where a bare LLM is not:

  • Independent audit, not trust. Tyndale computes what you should owe from your real coverage terms and compares it against both the provider's bill and the insurer's EOB. A raw LLM (and most people) read the EOB and assume the insurer did the math right. Tyndale doesn't — it catches payer errors, not just provider errors.
  • Encounter verification. Tyndale translates each charged line item into plain language and asks you to confirm it matches your visit — catching phantom charges and upcoded visits a raw LLM can't see.
  • Grounded retrieval. All four knowledge collections are live. Claims about codes, rules, laws, and policies come from real retrieved sources — not the model's memory.
  • Citation enforcement. Layers 1 and 2 run. Every Tier B legal claim resolves to a real source or the output doesn't ship.
  • Voice tiering. Facts asserted, legal claims qualified-and-cited, recommendations framed with reasoning, outcomes never predicted.
  • Structured findings. Bill Detective and Math Person write structured findings to the case file — auditable, not just prose.
  • Point-in-time correctness. A 2024 claim is adjudicated against 2024 law. A raw LLM has no concept of this.
  • Confident-advocate voice + the anticipation principles. The product still thinks ahead, surfaces next steps, and makes asks trivial.
Critical correctness principle — applies to both versions
The EOB is audited, never trusted
Insurers miscalculate cost-sharing, misapply coverage, process in-network care as out-of-network, ignore the out-of-pocket max, and wrongfully deny — often downstream of a provider's incorrect submission. If Tyndale trusted the insurer's EOB as the right answer, it would be blind to the entire category of payer errors, which is half of what Tyndale exists to catch. So Math Person computes the member's responsibility independently from coverage terms first, then compares against both the bill and the EOB. The coverage data the user uploads in V1-Lite isn't there to save typing — it's the independent basis for the audit. This is the Independent Audit Doctrine; it's foundational and it ranks above everything else.

The upgrade: folding out, not rewriting

When you move to full Tyndale, you "promote" the folded-in work into dedicated subagents. The Lead Planner prompt's legal-research section becomes the Legal Researcher subagent prompt (already written — Task 19). The strategy-guidance section becomes the Strategist subagent prompt (Task 20). The inline code lookups get a dedicated Code Validator (Task 21). The Skills and tools they use already exist. This is expansion: the logic moves from one prompt into three, and the Lead Planner goes back to pure coordination.

Why fold into the Lead Planner specifically
The Lead Planner already speaks the voice and owns composition
In full Tyndale the Lead Planner composes the final answer from subagent findings. In V1-Lite it does a bit more of the thinking itself, but the output surface is identical. The user experience doesn't change between versions — only the internal division of labor does. That's exactly the kind of change that's invisible to users and clean to upgrade.
Section 05 · Deferrals

What's deferred, and what V1-Lite does instead

Deferring letter generation is the biggest scope cut. Here's how V1-Lite still delivers value in its place.

Letter generation → detect, explain, and direct

In full Tyndale, when a bill error is found, the Strategist + Document Generation Skill draft the appeal letter. In V1-Lite, that final drafting step is deferred. Instead, V1-Lite:

  • Audits independently (Math Person) — computes what the user should owe from coverage terms and compares against both the bill and the EOB, catching payer-side errors as well as provider-side. The user sees three numbers: billed, EOB-claimed, and Tyndale-computed.
  • Verifies the encounter — translates each charged line item to plain language and has the user confirm it matches their visit, catching phantom charges and upcoded visits.
  • Detects the error (Bill Detective, identical to full).
  • Explains it clearly in plain language — what's wrong, why it's wrong, with the legal citation (Tier B).
  • Tells the user exactly what to do — "Call UnitedHealthcare at the number on your card, reference claim #X, and tell them the MRI was applied entirely to your deductible when only $400 should have been. Ask them to re-process it." A specific, scripted next step (Tier C).
  • Captures the outcome via the feedback loop — did the user act? Did it work? This is gold for training the full version's letter generator.

This is still dramatically more than a raw LLM gives — it's a grounded, cited diagnosis with a specific action plan. What it doesn't do yet is write the letter for the user. That's the headline feature you add when you go full, and by then you'll have real outcome data on which problems and which scripts actually resolve.

A deliberate sequencing benefit
Deferring letters defers your highest-risk surface
Letter generation is exactly where citation faithfulness, hallucinated numbers, and your manual-review burden concentrate. By deferring it, V1-Lite ships with a lower-risk output surface (explanations and scripts, which the user executes and sanity-checks themselves) while you accumulate the real bill examples and outcome data that make the eventual letter generator far better and safer. You're not just shipping less — you're sequencing risk intelligently.
Section 06 · Feedback & learning loop

Learning from users and their bills, from day one

The most valuable asset Tyndale builds isn't code — it's a growing corpus of real bills, real errors, and real outcomes. V1-Lite captures this from the first user, feeding the same eval system you already designed.

This loop is new to both versions — it wasn't in the original three documents, and it belongs in both. Building it in V1-Lite means full Tyndale inherits a working learning system plus months of accumulated data.

The four-stage loop

1 · Capture
→
2 · De-identify
→
3 · Triage
→
4 · Promote
Real usage becomes labeled eval cases that make every future version measurably better.

Stage 1 — Capture

  • Explicit feedback: thumbs up/down on every Tyndale response, plus an optional "what was wrong?" with structured reasons (wrong number, missed an error, bad recommendation, confusing, etc.).
  • Implicit signals: did the user act on the recommendation? Did they come back and report an outcome? Did they correct an extracted value?
  • Bill examples: the uploaded documents themselves, plus the structured extraction and the findings — the full case, captured for potential training/eval use.
  • Outcome capture: a lightweight "Did this get resolved?" follow-up that records whether the diagnosis and script actually worked.

Stage 2 — De-identify (the HIPAA gate)

Non-negotiable
Using a bill to improve Tyndale requires separate consent + de-identification
Serving a user with their data is one permission. Using their data to improve the product is a different one. V1-Lite collects explicit, separate opt-in consent ("Help improve Tyndale by letting us learn from your de-identified bills"). Before any real example becomes a candidate training/eval case, it runs through the same Presidio + custom-recognizer pipeline specced in the full Developer Spec (§18). No real example enters the eval corpus with PHI intact. De-identified examples are reviewed by Brock before promotion.

Stage 3 — Triage

  • Negative feedback and corrections are queued for Brock's review. A bad output is a candidate eval case — it shows a failure mode worth testing against.
  • High-value cases (clear errors Tyndale caught well, or clear misses) get flagged for promotion.
  • The triage queue routes to the same #tyndale-quality channel from the full failure-mode instrumentation (§22).

Stage 4 — Promote into the eval suite

  • Promoted cases are written in the same golden-example schema from Task 26 (evals/golden/schema.json) — so they slot directly into the eval suite you already designed.
  • A real bill that Tyndale got wrong becomes a regression test: the next version must get it right.
  • A real bill that Tyndale got right becomes a guardrail: future changes can't break it.
  • This is exactly the "eval suite grows from production findings" discipline rule (D21.10) — now fed by a real pipeline instead of waiting for the full version.
Why this matters more than it looks
By the time you build the letter generator, you'll know what actually works
Because V1-Lite captures which diagnoses and which action-scripts led to resolved bills, the full version's Document Generation Skill won't be authored from theory — it'll be trained and evaluated against real cases with known outcomes. The deferral of letter generation and the feedback loop work together: defer the hard feature, gather the data that makes it good, then build it well.

Forward-compatibility of the loop

The capture schema, consent model, de-identification pipeline, and promotion-to-golden flow are identical in both versions. Full Tyndale inherits the loop running and the data already accumulated. The only difference is volume — more users, more bills, more outcomes.
