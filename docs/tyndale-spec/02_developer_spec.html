Section 01 · Foundations

Six operating principles that shape everything

These principles are the operational interpretation of Tyndale's "thinks 5 steps ahead" product promise. They constrain every Skill prompt, every subagent design, every tool design. When a build decision is ambiguous, defer to whichever interpretation best honors these principles.

  1. P1 — Anticipate, then ask, then make the ask trivial. Before asking the user for information, exhaust inference from existing context (FHIR data, prior cases, the bill itself, payer policies, user state) and tool lookups. Only after those, ask. When asking, ask the one question that unlocks the most. Tell the user exactly how to find the answer in the most efficient way possible. Offer to help with the asking when Tyndale can (drafting a message, providing a script, making a call). "Go figure it out" is never the right answer. "Here's the one thing to ask, here's exactly how to ask it, and here's what to listen for" is.
  2. P2 — Surface what's next. When Tyndale completes a task, it doesn't stop at "done." It surfaces the next 1–2 things the user should consider: an upcoming deadline, a related bill that's likely affected, a follow-up action that's now possible. The user can ignore the surfacing, but they shouldn't have to ask for it.
  3. P3 — Bundle questions and actions. If Tyndale genuinely needs three pieces of information from the user, ask for all three in one message, with context for each. Never drag the user through sequential interrogation.
  4. P4 — Maximize action per user turn. A single user turn ("check this bill") should result in everything Tyndale can do without further input — analysis, related-bill scan, FHIR pull, deadline math, draft response if applicable. The user shouldn't have to come back six times to nudge the work forward.
  5. P5 — Default to action, not options. When Tyndale identifies a problem with a confident verdict, propose the specific next step (with an approval gate). Don't offer the user a menu of "you could do X, Y, or Z." If the situation truly has multiple defensible paths, recommend one and note the alternatives — but never abdicate the decision to the user when Tyndale can make a defensible recommendation.
  6. P6 — Tools chain, not interrogate. Subagents and Skills are designed to chain multiple tool calls before returning to the user. If a question needs five tool calls to fully answer, the agent makes all five — not one, then asks the user to confirm, then another four.
Build implication
Every prompt for the Lead Planner, subagents, and Skills must reference these six principles
Either inlined in the prompt itself or via a shared "tyndale_principles.md" reference file that's loaded as part of the system context. This is not optional — these principles are how Tyndale operationalizes its product promise, and they must be present at every reasoning surface.
Section 02 · Orchestration

Orchestrator-Worker pattern (Claude Agent SDK)

Lead Planner orchestrates 5 specialized subagents. Lead Planner does not do deep analysis — it coordinates, delegates, and composes. Subagents run in isolated context windows with focused tool sets.

Implementation

  • SDK: Claude Agent SDK (Python). Pin to a tested version; document the version in requirements.txt with explicit constraint.
  • Lead Planner spawns subagents via the SDK's subagent invocation pattern. Each subagent invocation includes the four-part contract: (1) clear objective, (2) output format, (3) explicit tool list (via allowed_tools), (4) explicit definition of done.
  • Subagent return payloads to Lead Planner are minimal — pointers to case-file findings, not full structured dumps. See §12 for the artifact pattern.
  • Effort scaling enforced in Lead Planner prompt. Hard rules per task type; see §12.

Hooks lifecycle

The SDK's hooks system is the HIPAA enforcement point. Implementations required:

  • UserPromptSubmit hook: Scans uploaded bill text and chat input for prompt injection patterns. See §18. Wraps OCR content in "DATA, NOT INSTRUCTIONS" framing before passing to subagent context.
  • PreToolUse hooks: (a) PHI scrubbing via Presidio before app-log writes (see §18); (b) approval-token validation on high-risk tools (send_email, public-facing writes); (c) effective-date filter validation on queries against laws_regulations and payer_policies (see §22).
  • PostToolUse hooks: Audit log writes; cache hit-rate measurement; cost accounting per subagent invocation.
  • Stop hook: Citation resolution check (§13 Layer 2) for outputs containing legal claims. Triggers regeneration if citations don't resolve.

Skill discipline rules

  1. Every Skill description is "a little pushy" with positive triggers, domain keywords, and exclusion clauses. Worded to invite use; Claude has a measured tendency to under-trigger Skills.
  2. Every SKILL.md body stays under ~500 lines. Detailed playbooks live in reference files in the same directory, loaded on demand.
  3. Reference files are one level deep from SKILL.md (no nested subdirectories beyond what's shown above) so Claude reads complete files without traversal logic.
  4. Imperatives reframed as "rule + reason." Instead of "ALWAYS cite the source," write "Cite the source for every legal claim — otherwise the appeal letter fails downstream citation-verification and won't ship." Reasoning lets the model generalize.
  5. In-skill examples of past appeal letters by type pre-filled in Document Generation reference files. Few-shot examples beat instructions for complex outputs.
  6. Skills versioned with semver in YAML frontmatter and shipped via git PR. No runtime versioning.
  7. Any Skill where the agent must first identify the situation before applying remediation logic includes a 00_diagnostic_index.md reference file loaded at the start of every invocation. Detailed remediation playbooks load only after the diagnostic identifies what's in play. Applies to: bill_error_detection, negotiation_strategy, charity_care_eligibility.

Section 06 · Knowledge

Four Qdrant knowledge collections

Collections hold factual reference data — codes, rules-as-data, statutes, policies. Behavior lives in Skills, not collections. Mandatory point-in-time filters on time-sensitive collections.

Collection Contents Refresh Size
billing_codes CPT, HCPCS, ICD-10 descriptors; categories; valid modifiers per code Quarterly ~80K rows
error_detection_rules NCCI PTP edits (narrative text only), MUE narrative, modifier validity, ACA §2713 preventive list, timely filing, upcoding patterns, phantom-charge red flags Quarterly ~250K rows (narrative); NCCI/MUE tabular data in Postgres separately
laws_regulations Federal + state laws (ERISA, ACA, NSA, MHPAEA, IRS 501(r), state surprise-billing, state medical-debt, state DOI) Weekly diff scan via Regulation Researcher cron ~12K chunks
payer_policies CMS LCDs/NCDs, Medicare Coverage Database, Part D formularies, HRSA 340B, commercial payer medical-necessity, prior-auth requirements Quarterly ~30K chunks

Discipline rules

  1. No behavioral rules in collections. "When you see X, do Y" content goes in Skills, not in Qdrant. Collections hold facts; the model interprets and decides.
  2. Mandatory point-in-time filters. Every query against laws_regulations and payer_policies must include an effective-date filter pinned to the relevant date (date-of-service for a bill; today's date for new questions). Enforced via PreToolUse hook (see §22).
Critical separation
NCCI edits and MUE limits live in structured Postgres tables, not Qdrant
Only the narrative policy text (CMS manual chapters, payer guidance) goes into the error_detection_rules Qdrant collection. Queries for "are these two codes bundled?" hit Postgres directly via ncci_check_pair and mue_check tools. Queries for "what's the policy rationale behind this rule?" hit Qdrant. This split is non-negotiable — treating tabular rule tables as text RAG and getting fuzzy matches on code pairs is a known production failure mode.

Pre-launch benchmark requirement

Ship gate — Josh owns
voyage-context-3 vs voyage-3-large NDCG@10 benchmark on laws_regulations
Before V1 ships, Josh runs an internal NDCG@10 benchmark on a curated 100-query legal eval set. Ship with voyage-context-3 only if it wins by ≥3 NDCG points. If not, revert to voyage-3-large. Document the result in benchmarks/embedding_choice.md with the eval set, methodology, and decision.

Reranking

  • Reranker: voyage rerank-2.5 for all RAG queries. No "fast path" that skips reranking.
  • Top-K from embedding search: 50. Top-K returned from rerank: 5–10 depending on query complexity.
  • Instruction-following used per-collection. Each collection has a default rerank instruction tuned to its domain. Subagents can override per query.
  • Rerank scores persisted in audit log for post-hoc debugging ("did the right chunk come back at rank 1, or rank 6?").

Default rerank instructions

# laws_regulations
"Prefer statutory law over case law. Prefer federal authorities over
state when the question implicates ERISA preemption. Prefer current
law over superseded provisions."

# payer_policies
"Return only policies effective on the date of service. De-prioritize
policies from the wrong plan year. Prefer payer-specific over generic."

# error_detection_rules
"Prefer NCCI edits over general billing guidance. Return rules
specific to the code combination, not parent category."

# billing_codes
"Prefer exact code matches over similar codes. Return the descriptor
for the queried code first."

Discipline rules

  1. Josh runs pre-launch NDCG benchmark per above. Ship gate.
  2. No mid-flight embedding model changes without re-embedding the full collection. Mixing two embedding models in one collection produces silently wrong results. Version collections (e.g., laws_regulations_v2) on any embedding model change.
  3. Embedding model and dimension locked in collection metadata. Code that queries the collection verifies the model match before embedding the query. Silent invalidator guard.
  4. All RAG queries go through rerank. No exceptions.
  5. Instruction-following used aggressively. Defaults above; subagents can override per query.
Section 08 · Hybrid search & chunking

Hybrid search on all collections; chunking per collection

Hybrid search

Hybrid (vector + BM25) on all 4 collections. RRF (Reciprocal Rank Fusion) for merging. Default fusion weight 0.5/0.5, tunable per collection. Qdrant ships hybrid natively.

Reason: vector-only fails on (a) statute citations like 29 U.S.C. § 1132(a)(1)(B), (b) CPT/HCPCS code exact matches, (c) plan-year date strings. Hybrid catches what either alone misses.

Chunking strategy per collection

Collection Chunking Avg size Storage
billing_codesOne chunk per code100–300 tokQdrant only
error_detection_rulesStructured rules in Postgres; policy narrative text in Qdrant per rule (200–500 tok)Split storagePostgres + Qdrant
laws_regulationsOne chunk per statute/regulation section; parent Title/Part/Subpart heading inline at chunk top800–1,500 tokQdrant only
payer_policiesOne chunk per policy section500–1,000 tokQdrant only

Discipline rules

  1. Hybrid search (vector + BM25 with RRF fusion) on all 4 collections. No exceptions.
  2. NCCI edits and MUE limits live in structured Postgres tables, not Qdrant. Only narrative policy text from CMS goes into the error_detection_rules Qdrant collection.
  3. Section headings included inline at the top of every chunk for laws_regulations. Parent Title/Part/Subpart context as metadata, but the immediate section heading goes in the chunk text itself.
  4. Every payer_policies and laws_regulations chunk has effective_date_start and effective_date_end. Every query filters by date-of-service. Non-negotiable.
  5. Chunk boundaries respect document structure. Section breaks, not fixed token windows.
  6. Chunk metadata schema is versioned alongside collection. Adding a new required metadata field means re-embedding.
Section 09 · Vector DB

Self-hosted Qdrant on Azure

Self-hosted Qdrant on Azure Container Apps inside the FastAPI monolith's VPC. No public ingress.

Discipline rules

  1. Self-hosted Qdrant on Azure Container Apps in same VPC as FastAPI monolith. No public ingress. Internal-only network policy.
  2. Quarterly Qdrant version upgrades scheduled in low-traffic windows (Sunday 03:00 UTC, alongside the Regulation Researcher cron's downtime if needed).

  5. No Qdrant Cloud migration until/unless Qdrant publishes a formal third-party HIPAA attestation. Revisit then.
Section 10 · Cron jobs

Two background workers

Proactive Monitor (nightly · 02:00 UTC)

Scans every active case file for:

  • Approaching deadlines (ERISA 180-day, ACA §2719, NSA windows, payer timely-filing, charity-care application deadlines). Configurable notification thresholds: 14d / 7d / 3d / 24h.
  • New EOBs from 1upHealth — auto-pull, OCR if needed, run through Bill Detective. Findings written to case file. Errors trigger user notification.
  • Inbound payer mail classification — approvals close cases; denials trigger Strategist; RFIs surface as user actions.
  • Urgency-tiered notifications: Urgent (SMS + push + email), Action (email + push), Success (email + push), Info (push or in-app only).

Regulation Researcher (weekly · Sundays 03:00 UTC)

  • CMS quarterly drops — NCCI edits, MUE limits, RVU updates, Medicare fee schedule. Re-indexes affected chunks in error_detection_rules and billing_codes; updates structured Postgres NCCI/MUE tables.
  • eCFR feeds — diffs ERISA, ACA, NSA, MHPAEA, IRS §501(r) regulations. Affected sections in laws_regulations get re-embedded with new effective dates; old versions get effective_date_end set.
  • State DOI updates per-state polling.
  • HRSA 340B daily check; CMS Coverage Database quarterly.
  • Routes material changes to the correction pipeline.
  • Writes last_verified_date back to chunk metadata.

Discipline rules

  1. Crons wrap stateless query() calls, not persistent agent sessions. Each case processed independently; each regulation source polled independently. Failure on one doesn't break the whole run.
  2. Idempotency by design. Running a cron twice produces the same result as running it once. Regulation changes are diff-based; notifications check for duplicates before sending.
  3. Cron runs logged to the same audit stream as user-triggered work.
  4. Failure alerts route to ops, not users. Failed cases get retried; persistent failures page on-call.
  5. Cost budgets per cron. Each cron has a daily/weekly cost ceiling. Exceeding budget pauses execution and alerts.

Tool description structure

Every tool description states:

  1. What the tool does in one sentence.
  2. When to use it — positive triggers.
  3. When NOT to use it — exclusion clauses.
  4. Arguments with concrete examples.
  5. Return shape with a sample.

  7. External MCP connector evaluation deferred to V1.1. When Anthropic's healthcare MCP connectors mature, evaluate whether any V1 in-process tools should migrate.
Section 12 · Context management

Artifact pattern + plan-to-memory + effort scaling

Artifact pattern (Postgres-backed)

Subagents write findings to Postgres case file. Lead Planner reads pointers to those findings, not full payloads.

# Subagent returns minimal payload to Lead Planner
{
  "finding_id": "fnd_a7d92...",
  "case_file_id": "case_847c1...",
  "summary": "Bundling error found; details in finding_id"
}

# Lead Planner reads from case file when composing user-facing output
finding = pg_case_file_get(finding_id)
# ...uses finding details only when needed

Plan-to-memory

Lead Planner writes plan to case file at start of complex tasks (active appeal, multi-step research, complex bill review). Plan includes:

  • What it'll investigate
  • What subagents it'll invoke
  • What success looks like
  • What it anticipates needing next after the current task completes (supports P2)

Plan is a versioned field; every revision logged. Subagents read current plan before doing work; if plan changed since subagent spawned, subagent re-reads and adapts.

Effort scaling rules

Hard rules embedded in Lead Planner prompt:

Task typeSubagents
Chat question, no case context0 (Lead Planner direct)
Pre-visit coverage check0 (Lead Planner via Plan a Visit Skill)
Cost estimation0 (Lead Planner via Cost Estimation Skill)
Clean bill check (no findings expected)2 (Bill Detective + Math Person)
Bill check with finding3 (Bill Detective + Math Person + Code Validator)
Active appeal5 (all subagents)

Lead Planner has judgment on ambiguous middle cases. Deviations from hard rules logged for review.

Discipline rules

  1. Subagent return payloads to Lead Planner are minimal — pointers, not dumps. Rich detail to case file.
  2. Lead Planner writes its plan to case file before complex work. Plan includes anticipated next steps.
  3. Effort scaling explicit in Lead Planner prompt. Reasoning required when deviating (logged).
  4. Context budget targets: <80K tokens per subagent invocation, hard ceiling 130K. Past 130K, subagent pre-compacts (writes intermediate work to case file, reloads only what's needed).
  5. Citation chains preserved across compaction. Write findings with embedded source IDs to Postgres before SDK auto-compaction can drop the original chunks.
  6. No subagent operates on stale plans. Subagents read current plan from case file before working.
Section 13 · Citation enforcement

Three-layer enforcement; Layers 1 + 2 at V1

Layer 1 — Generation-time discipline (prompt-level)

Every Skill and subagent prompt that generates a legal claim must enforce:

  • "No legal claim is asserted without a retrieved source"
  • "Every cited authority must include the source ID of the chunk it came from"
  • "If you cannot find a retrieved source for a claim, omit the claim rather than assert it without a citation"

Carried in: Document Generation Skill, Negotiation & Strategy Skill, Bill Error Detection Skill, Coverage Connection & FHIR Skill, Legal Researcher subagent prompt, Strategist subagent prompt.

Layer 2 — Programmatic citation resolution (Stop hook)

Standard citation format used everywhere — defined and locked at V1. Suggested:

# Format: [authority §section, source_id]
# Example: "[ERISA §503, src_a8f3e7]"
# OR using Anthropic's Citations feature where possible

# Stop hook flow:
# 1. Parse generated output for citation markers
# 2. For each marker, resolve source_id against chunks retrieved this session
# 3. If unresolved, reject output and trigger regeneration
# 4. After 3 failed regeneration attempts, flag for human review

Layer 3 — Faithfulness check (V1.1+)

Deferred to V1.1. Substitute at V1: Brock manually reviews every generated appeal letter before send. Earlier trigger if any "right form wrong substance" failures appear in production.

Discipline rules

  1. Every generated legal claim has a citation. No exceptions. Enforced in Skill and subagent prompts.
  2. Citation format consistent and machine-parseable. Standard format defined and locked at V1.
  3. Every retrieved chunk carries a source ID that gets logged at retrieval and embedded into citations.
  4. Layer 2 is a hard ship gate. Output fails Layer 2 = output does not ship. After 3 failed attempts, flagged for review and user gets a polite "taking longer than usual" message.
  5. Manual human review of every generated appeal letter at V1. Brock reviews each one before send.
  6. Regulation Researcher cron writes last_verified_date to every chunk. Citation resolver flags chunks with last_verified_date older than 90 days as "stale source."
  7. Anthropic's Citations feature in the Messages API used wherever possible to make Layer 2 cheaper and more reliable.
Section 14 · Voice tiering

Three-tier voice framework

The tiers

TierType of claimVoice rule
AFactual claims from structured data (numbers, codes, dates, names)Assert directly. No hedging. Values come from Math Person, Bill Detective findings, document parsing, or knowledge collection lookups.
BLegal interpretation with strong source supportConfident framing + qualifier + citation. Use "appears to," "qualifies for," "is entitled to" + cited authority. Always cite.
CStrategic recommendationFrame as recommendation with reasoning. "I recommend X because Y." Never predict outcomes.

Discipline rules

  1. Tier A facts come from structured inputs only. No numeric value, dollar amount, percentage, code, date, or named entity in any generated output is invented by the model. Document Generation Skill explicitly forbids emitting unstructured numbers.
  2. Tier B claims use standard qualifiers and always cite. "Appears to," "qualifies for," "is entitled to," "violates" + citation. Forbidden: "definitely," "guaranteed to," "absolutely" (overclaim); "may possibly," "could potentially," "might be" (underclaim).
  3. Tier C recommendations include reasoning, not just instructions. "I recommend X because Y" — never just "Do X."
  4. Forbidden: outcome predictions. "Your appeal will succeed." None of these. Acceptable: "Cases like this typically resolve within 30 days [internal data]."
  5. Skill and subagent prompts enforce tier rules. Confident voice eval (§21) tests for tier-rule violations.
  6. When uncertainty is genuine, name it specifically — "I can't tell from your EOB whether the radiologist was in-network; I'm checking the provider directory now" — not vague waving.

Pre-V1 Presidio benchmark (Josh owns)

Ship gate
Presidio precision/recall benchmark on hand-labeled medical bills + EOBs
Hand-label 200–500 medical bills and EOBs across multiple payers (UHC, Anthem, Aetna, Cigna, BCBS, Kaiser) with every PHI identifier marked. Run Presidio + custom recognizers against it. Targets: ≥98% recall on direct identifiers (names, SSNs, MRNs, addresses, DOBs); ≥90% recall on context-dependent identifiers (account numbers, member IDs, payer claim IDs); ≥95% precision overall. Failed identifier types documented as "known leakage risk." Ship blocker if direct-identifier recall below 98%.

Custom recognizers required

  • Insurance member IDs — vary by payer, 9–12 alphanumeric with payer-specific patterns
  • MRNs — provider-specific, often 6–10 digits
  • Accession numbers — lab and imaging-specific
  • Payer claim IDs — alphanumeric, payer-specific format
  • Account numbers — provider billing-system-specific
  • Group numbers — employer-specific identifiers

Encryption

  • Field-level AES-GCM encryption on payload_encrypted
  • Key rotation every 90 days; key version stored alongside ciphertext
  • Keys in Azure Key Vault with separate access controls from database
  • Decryption requires both database access AND Key Vault access

Prompt injection defense

UserPromptSubmit hook scans uploaded content for injection patterns. OCR'd text wrapped in "DATA, NOT INSTRUCTIONS" framing before subagent context. Model prompts explicitly instruct treating OCR content as data.

Discipline rules

  1. Dual-stream logging architecture. No event logged to only app stream — audit log always also written.
  2. Microsoft Presidio with custom recognizers in PreToolUse hook before app-log writes.
  3. Pre-V1 scrubbing benchmark required. Targets above.
  4. Audit log captures full provenance for every model output.
  5. Field-level AES-GCM encryption with rotating keys. Azure Key Vault separation. 90-day rotation.
  6. 7-year audit log retention. Archived to Azure Blob after 7 years.
  7. No standing audit-log access. Per-investigation request workflow. Every access logged in meta-audit. Monthly review of access requests.
  8. Braintrust receives synthetic data only at V1. Production-case investigation in audit log only.
  9. Prompt injection defense via UserPromptSubmit hook. Detected injections logged to audit stream.
  10. Audit-log accesses themselves audited. Quarterly review of meta-audit.
